# `Arg::Value`: Hash と Array を `Rubevy.ask` で運ぶ（2026-09-16）

sabiruby の `docs/plans/leftovers-plan.md` の 7 番。`Rubevy.ask` の引数は数値と文字列と Entity しか運べず、
Hash や Array を渡すと `to_s` になっていた。ECS の橋の計画（`docs/plans/ecs-bridge-plan.md` 段階 A の「書き込み」）が
2 案のうち採らなかったほうがこれで、そのときの理由は「`Commands` の約束（後で反映）に合う」から書き込みは
`HostCommand` にする、というものだった。書き込みの話は決着済みなので、今回は**質問**の側だけを直す。

## 何が問題だったか

`src/lib.rs` の `ask` ネイティブは、引数を 1 つずつ次の順で振り分けていた（変更前、1261 行あたり）。

```rust
other => match vm.as_string(*other) {
    Ok(bytes) => Arg::Text(String::from_utf8_lossy(&bytes).into_owned()),
    Err(_) => Arg::Num(0.0),
},
```

`Vm::as_string`（sabiruby `src/vm.rs:3776`）は「文字列ならそのバイト列、そうでなければ `to_s` を呼ぶ」。
つまり `Rubevy.ask("path", {from: [1,2]})` はホストに `Arg::Text("{from: [1, 2]}")` として届いていた。
文字列として届いてはいるので「落ちてはいない」が、構造が構造であることの意味は全部消えている。
`nil` は `to_s` が空文字なので `Arg::Text("")` になり、これも「引数が無い」と区別が付かなかった。

## 決めたこと 1: 値を写さず、値そのものを運ぶ

同じリポジトリに先例が 2 つあり、**互いに逆の判断**をしている。

* `src/reflect.rs` の `RubyData` は、Ruby の値を Rust 側に**写し取る**（`read_ruby`）。理由はその doc コメントに書いてある
  とおりで、`entity[:Transform] = hash` の書き込みは「`&mut World` があって VM が無い」システムで起きるから、
  VM を持っている今のうちに全部読み出すしかない。
* `ScriptWorld::answer_value` は逆に、**ホストに `&mut Vm` を渡して値を組ませる**。`Answer` を入れ子にすると
  VM が既に持っているものの劣化コピーになる、というのが段階 A の worklog に書いてある判断。

質問の引数は後者と同じ状況にある。`take_requests` を呼ぶのは `ResMut<ScriptWorld>` を持つシステムで、
つまり `world.vm` を持っている。だから写し取る理由が無く、写し取れば `Answer` を入れ子にするのと同じ
「劣化コピー」を作ることになる。`Arg::Value` は Ruby の `Value` そのものを運ぶ。

入れ子については計画書の示唆どおり「配列の中の数値や文字列も `Arg::Value` の中身のまま」にした。
引数 1 つが `Arg` 1 つで、どの `Arg` になるかはその引数だけで決まる。配列を歩いて葉を `Arg` に開く案も
考えたが、それは形（どこまでが 1 つの配列か）を捨てることで、形こそが構造を渡したい理由なので採らない。

## 決めたこと 2: RAII の形（`Drop` に `Vm` は来ない）

計画書は「`Request` が drop されたときに解除する形にすると漏れない」と言っている。問題は
`Drop::drop(&mut self)` に `Vm` が渡らないことで、`gc_unregister` は `&mut Vm` を要る。
考えた案は 3 つ。

1. **`answer` のときに解除する。** `answer` は `queue` を `gc_unregister` しているので、そこに並べるだけ。
   だが答えられずに捨てられた `Request`（システムが panic した、ゲームが「この種類は知らない」と捨てた）が
   そのまま漏れる。計画書が避けたがっているのはまさにこれ。
2. **`Request` から `Clone` を外し、`Vm` を持つ「解放の手」を通してしか捨てられないようにする。**
   型で強制できるが、`Request` は `answer_with` に move され、`Clone` は既に公開 API で、
   ゲームが `Vec<Request>` に貯めるのが普通の使い方（`tests/entity.rs` の `Seen` がそうしている）。破壊的すぎる。
3. **2 段階にする。** 採用。`Drop` は「何を解放すべきか」を知っていて `Vm` を持たない。フレームの頭の掃除は
   `Vm` を持っていて何を解放すべきかを知らない。両者を `Arc<Mutex<Vec<ObjId>>>` でつなぐ。

`RootedValue` は `Arc<Root>` を持ち、`Root` の `Drop` が `ObjId` をその Vec に積む。`ScriptWorld::release_dropped_values`
が `tick_scripts` の先頭で Vec を空にして `gc_unregister` する。登録は `ask` ネイティブで**1 回だけ**行い、
以後は `Arc` の複製が何個あっても登録は 1 つ。だから `Request: Clone` のままでよく、複製が全部消えたときに
1 回だけ解放される（`tests/ask_value.rs` の `a_cloned_request_holds_the_value_until_the_last_clone_is_gone`）。

この形の代償は「値が `Request` より最大 1 フレーム長生きする」こと。逆側の間違い（1 フレーム早く死ぬ）が
起きないことのほうが大事なので、これで良いと判断した。掃除の場所を `tick_scripts` の先頭にしたのは、
スクリプトが走る直前が「`Vm` を持っている最後の瞬間」だからで、ここで解放すれば同じフレームの
コレクションで回収される（実測でそうなっている。下）。

`Mutex` の `lock()` が poisoned を返す場合は `into_inner()` で中身を取る。ここで id を捨てると、
この型が存在する理由そのものである漏れになるので、panic した別スレッドがあっても解放は続ける。

## 決めたこと 3: 速い道は残す

数値・文字列・Entity は今までどおりコピーして運ぶ。ホストはそれらを `Vm` 無しで読めるほうが良く、
実際 `examples/sensor.rs` も `rubevy_games` もそう読んでいる。変えたのは**文字列の判定**で、
`vm.as_string`（`to_s` を呼ぶ）から `vm.str_bytes`（String のときだけ `Some`）にした。これで
「String は `Arg::Text`、それ以外は `Arg::Value`」がきれいに分かれる。

副作用として振る舞いが 2 つ変わる。`nil`/`true`/`false` は `Arg::Text("")` ではなく `Arg::Value` になり、
`to_s` を定義したスクリプト自身のオブジェクトも `Arg::Text` ではなく `Arg::Value` になる。
どちらも今まで情報を捨てていた側なので直ったと見ているが、`host-api.md` に明記した。
immediate（`nil` など）はヒープの対象が無いので `RootedValue` の `root` は `None` になり、登録も解放も起きない
（`numbers_strings_and_entities_keep_their_fast_paths` が `release_dropped_values() == 0` で確かめている）。

## 読み出しの補助

`Request::value(i) -> Option<Value>` と `Request::arg_as::<T: FromRuby>(&self, vm, i) -> Option<T>`。
`arg_as` は sabiruby の `FromRuby`（`src/convert.rs:73`）に丸投げなので、`Vec<f64>`、`Vec<String>`、
`Vec<Vec<f64>>`、`f64`、`bool` などがそのまま取れる。変換に失敗したら `None` にした。
`num(i)`/`text(i)`/`entity_arg(i)` が「種類が違えば `None`」なのと揃えたかったからで、
`TypeError` を見たいホストは `request.value(i)` に自分で `T::from_ruby` を掛ければよい（rustdoc に書いた）。

Hash には `FromRuby` が無い（`convert.rs` にある実装は Value/i64/i32/f64/bool/String/Sym/Option/Vec/Bytes/DataRef で、
map は無い）ので、`Vm::hash_entries(v) -> Option<Vec<(Value, Value)>>` で 1 エントリずつ読む形を
`host-api.md` と `Request::value` の rustdoc の例に書いた。**これは今日の sabiruby main に入っていた**
（`src/vm.rs:1124`）。`leftovers-plan.md` の 8 番が言う「Hash のキー列挙」は VM 側が済んでいるので、
rubevy 側の `read_ruby` がまだ `funcall("keys")` で代用している（`src/reflect.rs:133`）のを差し替えれば
8 番のうち 1 つは閉じる。今回の範囲外なので触っていない。

## 確かめたこと

`tests/ask_value.rs` を 4 本。肝は「ホストが持っている値は VM のどこからも指されていない」状態を作ること
で、そうでないとコレクタの検証にならない。スクリプトはリテラルをメソッドの中で組み立て、
そのメソッドから戻ってからキューを待つ:

```ruby
def question
  Rubevy.ask("keep", [1.0, 2.5, 4.0], { name: "scout", ... }, Array.new(400) { |i| "s#{i}" })
end
q = question    # ここでリテラルを持っていたフレームは消える
GC.start
$answer = q.pop
```

ホスト側は `take_requests` のあと `answer` の前に `vm.gc_collect()` を呼び、そのあとで中身を読む。
`live_after_gc`（`Vm` の公開フィールド）で前後を測ると **held=1043 → after=633**、つまり解放後の
コレクションで 410 個が回収された。400 個の文字列＋配列 2 つ＋Hash＋キュー、で数が合う。

この検証が本当に検証になっているかを確かめるために、`RootedValue::new` の `gc_register` だけを外して
同じテストを走らせた（negative control）。結果:

```
thread '...' panicked at .../sabiruby/src/object.rs:703:9:
access to freed object ObjId(649)
```

登録が無ければ、ホストが読もうとした時点でオブジェクトは既に無い。つまりテストが見ているのは
「登録があるから生きている」であって、たまたま生きていたのではない。`gc_register` を戻して再度 4 本とも通る。

## 捨てた案・やらなかったこと

* **`RubyData` を公開して `FromRuby` を実装する**案。`request.arg_as::<RubyData>(vm, 0)` で Hash も Array も
  Rust 側の木として一発で取れて見栄えは良い。やめたのは (1) `read_ruby` が `funcall("keys")` で VM を回すので、
  ネイティブの外（ホストのシステム）から呼ぶ経路が増えること、(2) `Vm::hash_entries` が VM 側にできた今、
  写し取る木をもう 1 つ公開 API に増やす理由が弱いこと、(3) `RubyData` は書き込み（`set_component`）のための
  型で、そちらの都合（`MAX_DEPTH`、`Entity` variant）を質問側に持ち込むことになる、の 3 つ。
* **`answer` のときに解放する**案。上の 1 番。漏れる。
* **`Request` から `Clone` を外す**案。上の 2 番。API が壊れすぎる。
* `examples/` は足していない。`sensor.rs` は「1 フレームを跨ぐ質問」を見せる例で、そこに Hash を足しても
  見せたいものが増えない。テストのほうが具体的に書けている。
* `src/reflect.rs` の `funcall("keys")` → `Vm::hash_entries` の差し替え（`leftovers-plan.md` 8 番）は触っていない。
