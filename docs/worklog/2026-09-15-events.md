# イベントの受け口（段階 B）

2026-09-15、段階 A の続き。指示書は `docs/plans/ecs-bridge-plan.md` の段階 B。ブランチ `ecs-bridge`。

## 前提の確認

計画書の通り、新しい VM の機構は要らなかった。`Rubevy.ask` が既に `Task::Queue` を作って返し、
スクリプトはその上で待っている（`src/lib.rs` の `ask` ネイティブ）。イベントは「答えを 1 つ入れるキュー」を
「何度も入れるキュー」にするだけで、待つ側の仕組みは同じ。`pop` が待てるのはそれが Ruby のメソッドだから
（段階 A の worklog に書いた C 関数境界の話と同じ）。

Bevy 側は `bevy_ecs-0.19.1/src/event/mod.rs:88` の `Event` と 327 行の `EntityEvent`（`event_target`）、
`bevy_app-0.19.1/src/app.rs:1474` の `add_observer`、`bevy_ecs-0.19.1/src/observer/system_param.rs:38` の
`On<'w,'t, E, B>` を見た。rubevy の `ScriptEnded` は `Message` のままで、これは触っていない
（`Message` は毎フレーム読む放送、`Event` は observer が受け取るもの、という bevy 0.19 の分け方）。

## 作ったもの

* `ScriptWorld::publish(entity: Option<Entity>, name, payload: Answer)` と
  `publish_value(entity, name, |vm| Value)`。前者は平らな `Answer`、後者は入れ子の値（エンティティを
  含む配列など）。段階 A で `answer`/`answer_value` を 2 本にしたのと同じ形にした。`Answer` から `Value` を
  作る `match` は `answer` と `publish` で共通なので、`answer_value(vm, answer, entity_class)` という
  自由関数に切り出した。
* `Rubevy.subscribe(:hit)` はネイティブ。`task_queue_new` して `gc_register` し、VM のホスト状態の
  `subscriptions: Vec<Subscription>` に `(entity, name, queue)` で足して、キューを返す。
* `entity_object(vm, class, entity)` と `ScriptWorld::entity_class()`。`publish_value` の中は `&mut Vm` しか
  無いので、エンティティを配列に入れたいホストが `Rubevy::Entity` を作れない。`Answer::Entity` は答え全体が
  エンティティのときしか使えないので、この 2 つを公開した。テストと `examples/events.rs` の両方で使っている。

## 決めた点

* **キューの上限は 64（`ScriptWorld::QUEUE_LIMIT`）で、溢れたら古いものから捨てる。** 計画書の勧め通り。
  上限が無いと、購読してから別のことを待っているスクリプトが、ゲームが送った全部を抱え込む。新しいものを
  捨てる（push しない）案もあるが、遅れて起きたスクリプトが欲しいのは「直近の 64 件」であって
  「最初の 64 件」ではないので、古いほうを捨てる。テスト `the_oldest_messages_are_dropped_when_nobody_reads`
  が 100 件送って、残り 64 件、先頭が 36 であることを見ている。
  捨てるのに使っているのは Ruby の `Task::Queue#__pop_try(true)`。`Vm` には非ブロッキングの pop も
  キューの長さを見る関数も無いので、`size` と `__pop_try` を `funcall` している（ホスト側からの呼び出しなので
  待つことは無い）。`Vm::task_queue_len` と `task_queue_try_pop` があれば素直になる。
* **購読を外す場所は 2 つ。** 計画書は「`ScriptTask` の `on_remove`」と書いていたが、それだけでは足りない。
  スクリプトが最後まで走り切ったとき、`ScriptTask` は**残る**（それが「二度目を走らせない」印になっている。
  `src/lib.rs` の `ScriptDone` の rustdoc）。だから `tick_scripts` がタスクの終了を見て `ScriptDone` を
  入れるところでも `unsubscribe(entity)` を呼ぶ。`on_remove` のほうは、エンティティが despawn されたときと
  スクリプトが差し替えられたときに効く。テストは両方ある
  （`the_subscription_goes_when_the_script_does`、`a_despawned_script_stops_listening`）。
* **`Task.new` で作ったタスクからの `subscribe` は断る。** 購読はエンティティに属する（エンティティ宛の
  メッセージが誰に届くか、いつキューを手放すか、がそれで決まる）。`Task.new` のタスクには
  `@rubevy_entity` が無いので、そこで購読すると、エンティティ宛が届かず、いつまでも外れないキューが残る。
  黙って壊れるより、`subscribe from the script's own task` と言って止めるほうがよい。計画書の例
  （スクリプト本体で購読して、`Task.new` の中で `pop` する）はそのまま動く。`examples/events.rs` の
  `events.rb` がその形。
* **Bevy のイベント型は自動で結ばない。** 計画書の通り。ゲームが observer を 1 つ書く:
  `app.add_observer(|on: On<Hit>, mut scripts: ResMut<ScriptWorld>| scripts.publish(Some(on.entity), "hit", …))`。
  テスト `an_observer_is_the_one_line_a_game_writes` がその 1 行を実際に動かしている。

## つまずいたところ

テストを 8 本書いて、最初は 2 本が落ちた。どちらも**同じフレームの中の順序**の問題だった。
ゲーム側の `answer_nil`（`take_requests` して答える system）は `Update` の中で、rubevy の
`(start_scripts, deliver_answers, answer_components, tick_scripts, drain_commands, apply_component_writes)`
の鎖との順序が決まっていない。だから「`Rubevy.ask("ready")` が答えられたフレーム」の中で、
`answer_nil` が先に走れば、スクリプトはそのフレームのうちに再開して次の行まで進む。

* `the_subscription_goes_when_the_script_does` は、`ready` の直後にスクリプトが最後まで走り切ってしまい、
  購読を数えたときにはもう 0 になっていた。スクリプトを `hits.pop` で止まる形にして、
  「待っている間は 1」「メッセージを 1 つ受けて終わったら 0」を見るようにした。こちらのほうが
  見たいこと（読む人がいなくなったキューは残さない）をそのまま書いている。
* `the_oldest_messages_are_dropped_when_nobody_reads` は、ホストが 100 件入れる前にスクリプトが
  `q.size` を読んでしまって 0 だった。`sleep` を挟んで、ホストが詰める間スクリプトを眠らせた。

そのあと `sleep 0.05` を使っていたテストが今度は時間切れで落ちた。テストの `frames()` は 1 フレームにつき
2 ms しか実際に眠らないので、20 フレームで 40 ms しか進まない。スクリプト側の `sleep` を 0.01 にして、
フレーム数を 25 にした。5 回続けて走らせて 8/8 が安定して通ることを確かめた。
