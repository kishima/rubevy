# rubevy の可能性（平易版）

2026-09-12。英語版 `outlook.md` の「Possibilities」を、読みやすい日本語で書き直したもの。
著者の方針は「速さで Lua と競わない。Ruby は DSL（記述のための言語）として強くする」。

## どうしてこういう夢が描けるのか

SabiRuby という VM には、ひとつ大事な性質があります。**VM の中身が全部ただのデータである**ことです。
レジスタも、呼び出しの積み重ねも、ヒープのオブジェクトも、Fiber も、Rust の普通の値として持っています。
C のスタックに隠れた状態はありませんし、longjmp のような飛び道具も使っていません。
時間と乱数は、ホスト（Bevy 側）から渡されたものしか使いません。命令数の予算で途中で止まれます。

「VM がプロセスではなく、値である」と言い換えられます。下の 7 つは、すべてこの性質から出てきます。

## 1. 動かしたまま作れるゲーム

エンジンの中にコンパイラが入り、`eval` と `load` が動くようになると、ゲームを動かしたまま Ruby を書き換えられます。
メソッドを定義し直した瞬間に、画面の NPC の動きが変わります。ゲームの中に Ruby の対話環境（REPL）を置いて、
エンティティに話しかけるように調べることもできます。

Ruby の DSL をライブコーディングの楽器にした前例が Sonic Pi です。音でできたことは、映像と遊びでもできます。

必要なもの: ホストの差し込み口（Host）、eval、デバッガの欄。どれも計画済みです。

## 2. スクリプトの状態を丸ごと保存する

VM の中身がデータなので、そのまま保存できます。すると、こんなことが自然にできます。

* `sleep` の途中で止まっているコルーチンごと保存されるセーブデータ
* 「時間を巻き戻す」をゲームの仕掛けにする
* リプレイ
* 対戦相手と同じ計算を同じ順に行い、状態のハッシュで食い違いを検出するネット対戦（ロックステップ）

再現性は、後から頑張って作るものではなく、VM の作りとして最初から保証されています。時間と乱数をホストからしか受け取らないからです。

必要なもの: VM の直列化（ヒープと Context を順に書き出す。1 週間程度）と、Rust の値を包んだオブジェクトをどう保存するかの決まり。

## 3. 1 本のカートリッジで 3 台の機械

同じ `.mrb` が 3 つの場所で動きます。

* Bevy の PC 版
* ブラウザ（Bevy の wasm 版、または Playground）
* マイコン級の機器（著者の family-mruby が自然な相手です）

Ruby で書いたゲームを、机の上でも、リンクを送った先でも、手のひらの機械でも同じように遊べる。
Ruby のファンタジーコンソールです。

必要なもの: 組込み向けのビルド（thumbv7em は CI で通っています）と、画面を描くための小さなホスト API。

## 4. 利用者や AI が書いたスクリプトを安全に動かす

VM には命令数の予算があり、ヒープの上限はホストが決められ、ファイルや通信には Host を通さないと触れません。
つまり、Mod や AI が書いたスクリプトは、

* フレームを止められない（無限ループしても予算で切れる）
* メモリを食い潰せない
* ファイルに触れない

という状態で動かせます。LLM は Ruby をよく書けるので、NPC の頭脳を遊んでいる最中に生成し、エンジン内でコンパイルして、
予算つきのタスクとして走らせる、という遊び方が視野に入ります。

「安全だ」と言えるのは、本家のテストスイートと本があるからです。主張ではなく根拠になります。

必要なもの: ヒープの上限、タスクごとの予算（task の計画）、スクリプトに何を許すかを決めるホスト側の方針。

## 5. 何千もの小さな心

mruby-task と Fiber を使うと、NPC ごとに Ruby のタスクを 1 つ持たせ、優先度で回し、ほとんどのフレームでは眠らせておけます。
VM 自体が小さい（no_std）ので、陣営ごとに 1 つでも、エンティティごとに 1 つでも持てます。

必要なもの: task（計画済み）と、GC を少しずつ進める入口（`gc_step`）。

## 6. 機械を見ながら学ぶ

Playground のために作るビジュアライザ（レジスタ、フレーム、環境、Fiber、GC を表示するもの）は、そのままゲームの窓にも出せます。
初心者が Ruby を書き、エンティティが動き、VM を開けば中でレジスタが動いているのが見える。
日本では Ruby が教育で使われています。中が透けて見えるゲームエンジンは、道具というより教材になります。

## 7. CRuby で試作して、Bevy で出す

スクリプトで使う Ruby の範囲は mruby のものなので、ゲームのルールを CRuby の道具（RSpec など）で先に試して、
そのままエンジンで動かせます。SabiRuby の独自テストは、mruby と CRuby の意味が同じところでは CRuby の出力と照合しています。

## 質問への答え: ECS のエンティティは Ruby のオブジェクトになるか

**なります。それが ECS の橋（計画の 3 と 4）の中身です。** 見た目はこうなる予定です。

```ruby
e = spawn(Sprite.new("player.png"), Transform.at(0, 0))   # Entity を包んだ Ruby オブジェクト
e[:Transform].translation.x += 1.0                          # コンポーネントに名前で触る
e.add(Velocity.new(x: 2.0))
e.despawn

each(:Enemy, :Transform) { |enemy, tf| tf.translation.y -= 1 }   # クエリもブロックで
```

仕組みは 3 段です。

1. **Rust の値を包む Ruby オブジェクト**。mruby の `RData` にあたるもの（SabiRuby では `ObjKind::Data`）に `Entity` を入れます。
   Ruby からは普通のオブジェクトに見え、GC で回収されるときに Rust 側の `Drop` が走ります。
2. **コンポーネントは Bevy のリフレクションで触る**。Bevy の `Reflect` を使うと、コンポーネントのフィールド名と型が実行時に分かります。
   Ruby の `method_missing` と組み合わせれば、コンポーネントの種類ごとに接着コードを書かなくても、`tf.translation.x` のように名前でたどれます。
   型ごとに手で書くのは、速さが要る少数のものだけです。
3. **書き込みは step の後にまとめて反映**。VM を回す間だけ `&mut World` をホストに貸し、Ruby からの `spawn`／`add`／`despawn` や値の変更は
   Bevy の `Commands` と同じように一度ためて、step が終わってから適用します。VM がホスト呼び出しの途中で Ruby に戻らない作りなので、これが安全にできます。

読み取りはその場の値が返ります。書き込みが遅れて見える点は `Commands` と同じ約束なので、Bevy を知っている人には馴染みがあります。

順序としては、まず Host の差し込み口、次に `.rb` をアセットにしてホットリロード、その次がこの橋です。
橋を作るときは「毎フレーム大量に読み書きする」形ではなく、「宣言時に組み立てて、イベントとコルーチンで少しだけ触る」形を先に作ります。
DSL として使う方針に合っていて、性能の弱点が効かない使い方だからです。

## 補足: Rust のメモリ安全は Ruby 側にも効く（2026-09-12、著者の指摘）

SabiRuby の VM crate に `unsafe` は 1 か所だけです（命令のバイト値を範囲確認したうえで enum に変換する箇所）。
つまり VM の中で起きうる不具合は「間違った値」「例外」「panic」であって、「メモリ破壊」ではありません。
本家 mruby は C なので、GC のバグや境界の誤りが黙ってメモリを壊し、脆弱性になってきました。SabiRuby ではそれが起きません。

Ruby 側から見ると次の意味があります。

* Ruby のプログラムがどんな値を作っても、VM がメモリを壊すことはない。ホスト（ゲーム）が道連れになるとしたら panic であって、静かな破壊ではない
* GC の根の漏れは、メモリ破壊ではなく「回収済みのオブジェクトへの参照」として検出される（ストレスモードの assert）
* ネイティブメソッド（Rust で書く拡張）も生ポインタが要らないので、mruby の C 拡張で最も多い落ち方（解放済みメモリの参照、アリーナの溢れ）が無い
* 4 番の「利用者や AI が書いたスクリプトを安全に動かす」の前提が、VM の作りとして満たされている

限界も書いておきます。コンパイラは本家の C のまま（Prism とコード生成）なので、ソースを読む段階は Rust の保証の外です（Prism はよくファジングされていますが）。
panic は安全ですが止まります。ゲームで使うなら「VM は panic しない」を目標にする作業（`unwrap`／`expect`／`panic!` は今 122 か所。多くは内部の不変条件）と、
ホスト側で `catch_unwind` する備えが要ります。メモリ安全は「意味が正しい」ことを保証しません。正しさは本家のテストで測っています。

## 補足: 本体は Rust、一部だけ Ruby という使い方（2026-09-12、著者の質問）

それが rubevy の想定する形そのものです。Ruby は「全部を書く言語」ではなく、Rust のゲームに**部分的に差し込む**ものです。

* Rust が持つもの: ゲームループ、描画、物理、入力、大半の system。今までどおりの Bevy です
* Ruby を付ける場所: `Script` コンポーネントを付けたエンティティ（NPC の挙動）、シーンを組み立てる `.rb`（DSL で spawn）、イベントの受け口
* Ruby を付けないエンティティには何の影響もない。Ruby の VM は `Script` が付いたぶんだけ作られ、Rust の system が決めたタイミング（どのスケジュール、どの予算）でだけ動く

```rust
// Rust 側: 普通の Bevy。NPC にだけ Ruby を付ける
commands.spawn((Npc, SpriteBundle { .. }, Script::new(asset_server.load("npc/guard.rb")).with_budget(20_000)));
// Ruby から呼べる関数を登録する（ネイティブメソッド。生ポインタは要らない）
rubevy.define("play_sound", |vm, args| { /* Rust の処理 */ Ok(Value::Nil) });
```

```ruby
# npc/guard.rb: 挙動だけ Ruby。フレームをまたぐ動きはコルーチンで
on(:player_seen) { |player| chase(player) }
loop do
  patrol_to(:point_a); sleep 2
  patrol_to(:point_b); sleep 2
end
```

Ruby 側のミスがゲーム全体に及ばないことも、この形の利点です。命令数の予算で 1 フレームに使える時間が決まり、例外は `ScriptError` イベントになり、
メモリ破壊は起きません。リリース時に Ruby を外したければ、`Script` を付けなければよいだけです（機能ごと feature で外すこともできます）。

今の v0 で既にある: エンティティごとの VM、毎フレームの予算つき実行、`$frame`／`$delta`、ログ。足りないのは ECS の橋（エンティティを Ruby から触る）、
イベントの受け口、Host（コンパイラと時計）で、どれも計画の前半にあります。

## 補足: Rust と Ruby の相互呼び出し（2026-09-12、著者の質問）

どちらの向きもできます。mruby の C 拡張と `mrb_funcall` に相当するものが、そのまま Rust にあります。

* **Rust → Ruby**: `vm.funcall(receiver, method_sym, &args, block)`、ブロックなら `vm.call_block(blk, &args)`。戻り値は `Result<Value, VmError>`
* **Ruby → Rust**: ネイティブメソッドは `fn(&mut Vm, self, &[Value], block) -> VmResult<Value>` の Rust 関数。`vm.define_method(class, "name", f)` で登録する
* **Ruby → Rust → Ruby**: ネイティブの中で `vm.funcall` を呼べる。VM は入れ子の実行ループを Rust のスタック上で回す（本家の `mrb_funcall` → `mrb_vm_run` と同じ形）。
  何段でも入れ子にできる

```rust
fn each_enemy(vm: &mut Vm, _self: Value, args: &[Value], blk: Value) -> VmResult<Value> {
    for e in enemies() {                       // Rust 側のデータ
        let obj = wrap_entity(vm, e);          // Entity を Ruby オブジェクトに
        vm.call_block(blk, &[obj])?;           // Ruby のブロックを呼ぶ。例外は `?` で伝わる
    }
    Ok(Value::Nil)
}
```

本家と違って良くなる点が 1 つあります。Ruby 側の例外は longjmp ではなく `Err` として Rust に戻るので、`?` で素直に伝えられ、
途中の Rust の値の後始末（`Drop`）が必ず走ります。本家の C 拡張では longjmp が C の途中の処理を飛び越えるので、資源の解放を自分で守る必要がありました。

約束事（本家と同じもの）:

* ネイティブの実行中は GC が回収しない（`native_active`）。Rust の手元にある `Value` は安全だが、長いネイティブは GC を遅らせる
* ネイティブの境界をまたいで Fiber を切り替えることはできない（`FiberError`。本家と同じ制約）
* 命令数の予算による中断は、入れ子の実行ループの中では効かない。ネイティブから呼んだ Ruby メソッドが長いと、戻ってくるまで止まれない。
  毎フレームの予算で止めたい処理は、ネイティブ経由ではなくトップレベルの Ruby から呼ぶ形にする
