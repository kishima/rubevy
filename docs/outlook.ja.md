# rubevy の可能性（平易版）

2026-09-12 に書き、2026-09-14 に現状に合わせて更新。英語版 `outlook.md` の「Possibilities」を、読みやすい日本語で書き直したもの。
著者の方針は「速さで Lua と競わない。Ruby は DSL（記述のための言語）として強くする」。

実際に Rust と Ruby がどうつながっているか（`Rubevy.ask`、時間の上限、C の mruby を組み込んだ場合との比較）は
`rust-bridge.ja.md` に書いた。この文書は「何ができそうか」と「どこまで来たか」の見取り図。

## 現状のまとめ（2026-09-14）

|---|---|---|

| 2. 状態を丸ごと保存する | まだ | 再現性の土台（命令数のタイムスライス、決まった乱数の種）はある。VM の直列化は未着手 |

## どうしてこういう夢が描けるのか

SabiRuby という VM には、ひとつ大事な性質があります。**VM の中身が全部ただのデータである**ことです。
レジスタも、呼び出しの積み重ねも、ヒープのオブジェクトも、Fiber も、Rust の普通の値として持っています。
C のスタックに隠れた状態はありませんし、longjmp のような飛び道具も使っていません。
時計はホスト（Bevy 側）から渡されたものしか使わず、乱数の種は決まった値か、プログラムが `srand` で与えたものです。
命令数の予算で途中で止まれます。

「VM がプロセスではなく、値である」と言い換えられます。下の 7 つは、すべてこの性質から出てきます。

## 1. 動かしたまま作れるゲーム — **一部できました（2026-09-14）**

エンジンの中にコンパイラが入り、`eval` と `load` が動くようになると、ゲームを動かしたまま Ruby を書き換えられます。
メソッドを定義し直した瞬間に、画面の NPC の動きが変わります。ゲームの中に Ruby の対話環境（REPL）を置いて、
エンティティに話しかけるように調べることもできます。

Ruby の DSL をライブコーディングの楽器にした前例が Sonic Pi です。音でできたことは、映像と遊びでもできます。

**いまできること**: SabiRuby Battle（`sabiruby/rubevy_games`）では、ロボットの頭脳（`.rb`）をゲームの中のエディタで書き換え、
F5 でそのロボットだけに即反映できます。反映はメモリの上だけで、残したいときに保存します。外のエディタでファイルを保存すると、
そのファイルを使うロボットが新しい頭脳で動き直します。ブラウザ版でも同じエディタが動き、保存先はブラウザの中です。
土台として、ホストの差し込み口（`Host`）、`eval`、`require`／`load`、ゲーム内でのコンパイルが入っています。

**まだのこと**: 差し替えは「タスクを止めて新しい頭脳で起動し直す」形で、動いているタスクの状態（インスタンス変数など）は引き継ぎません。
メソッドだけを定義し直してそのまま動き続ける形と、ゲーム内の REPL はこれから。

## 2. スクリプトの状態を丸ごと保存する

VM の中身がデータなので、そのまま保存できます。すると、こんなことが自然にできます。

* `sleep` の途中で止まっているコルーチンごと保存されるセーブデータ
* 「時間を巻き戻す」をゲームの仕掛けにする
* リプレイ
* 対戦相手と同じ計算を同じ順に行い、状態のハッシュで食い違いを検出するネット対戦（ロックステップ）

再現性は、後から頑張って作るものではなく、VM の作りとして最初から保証されています。時計をホストからしか受け取らないからです。

**現状**: 直列化はまだ手を付けていません。再現性の側は整いました。タイムスライスは既定で命令数で切れるので、
どのマシンでもタスクの切り替わる位置が同じです。時間の上限（4 番）はフレームを守る安全装置で、通常のプレイでは発動しません。
時間だけでスライスを切る設定もありますが、それを選ぶと再現性は失われます（`sabiruby/docs/gems.md` の mruby-task、「Time limits」）。
SabiRuby Battle の試合は `seed:` を指定すると乱数の出目がそろいますが、フレームの間隔や答えが返るタイミングが違うので、
今は「同じような試合」であって「同じ試合」ではありません。

必要なもの: VM の直列化（ヒープと Context を順に書き出す。1 週間程度）、Rust の値を包んだオブジェクトをどう保存するかの決まり、
ゲーム側を固定タイムステップにすること。

## 3. 1 本のカートリッジで 3 台の機械 — **2 台できました（2026-09-14）**

同じ Ruby が 3 つの場所で動きます。

* Bevy の PC 版
* ブラウザ（Bevy の wasm 版、または Playground）
* マイコン級の機器（著者の family-mruby が自然な相手です）

Ruby で書いたゲームを、机の上でも、リンクを送った先でも、手のひらの機械でも同じように遊べる。
Ruby のファンタジーコンソールです。

**いまできること**: SabiRuby Battle は、同じコードから PC 版とブラウザ版をビルドし分け、ブラウザ版を
https://sabiruby.github.io/rubevy_games/ で公開しています（差は `sabibots/src/platform.rs` に集め、ビルドの対象で切り替え）。
ブラウザ版では、ゲームの中の VM（Rust）とは別に、Playground のコンパイラ（本家の C を wasm にしたもの）を読み込み、
ロボットの `.rb` をその場でコンパイルしています。VM 自体は C を必要としないので、あらかじめコンパイルした `.mrb` だけで遊ぶなら
モジュールは 1 つで済みます（`rubevy_games/docs/web.md`）。

**まだのこと**: マイコンは、VM が組込み向け（`thumbv7em-none-eabi`）にビルドできることを CI で確かめているだけです。
画面を描くための小さなホスト API と、実機のホストはこれから。

## 4. 利用者や AI が書いたスクリプトを安全に動かす — **大部分できました（2026-09-14）**

VM には命令数の予算があり、ファイルや通信には Host を通さないと触れません。
つまり、Mod や AI が書いたスクリプトは、

* フレームを止められない
* メモリを食い潰せない（← まだ）
* ファイルに触れない

という状態で動かせます。LLM は Ruby をよく書けるので、NPC の頭脳を遊んでいる最中に生成し、エンジン内でコンパイルして、
予算つきのタスクとして走らせる、という遊び方が視野に入ります。

「安全だ」と言えるのは、本家のテストスイートと本があるからです。主張ではなく根拠になります。

**いまできること**:

* **無限ループしてもフレームは止まらない**。タスクは命令数でタイムスライスが切れ、rubevy は毎フレーム命令数の予算で回します。
* **命令数では止められないものにも上限がある**（2026-09-14）。ネイティブの中で待たれているブロック（`sort { }`、`Array.new(1) { loop { } }`）は
  切り替えができず、以前はゲーム全体が固まりました。いまはフレームごとに時間の上限がかかり（rubevy の `frame_time` 8ms、`overrun` 50ms。
  時計は Bevy の `Instant`）、超えても抜けられないタスクには `Task::Overrun` が投げられます。`StandardError` ではないので、
  スクリプトの `rescue => e` では握りつぶせません。SabiRuby Battle のロボットにこの 1 行を書いても、そのロボットが止まるだけで試合は続きます。
* **止めたスクリプトは本当に止まる**。エンティティを消す、スクリプトを差し替えると、VM の中のタスクも終わります
  （以前は差し替えた古い頭脳が見えないところで動き続けていました。`tests/replace.rs`）。
* **例外はそのスクリプトだけの失敗になる**（`ScriptEnded { status: Failed }`）。他のスクリプトは動き続けます。

**まだのこと**: ヒープの上限（メモリを食い潰せない、はまだ言えません）、1 命令で重いネイティブ（巨大な文字列の `reverse` など）を途中で止めること
（戻ってから気づくのが限界）、スクリプトに何を許すかを決めるホスト側の方針。

## 5. 何千もの小さな心 — **できるようになりました（2026-09-13）**

mruby-task を使って、NPC ごとに Ruby のタスクを 1 つ持たせ、優先度で回し、ほとんどのフレームでは眠らせておけます。
VM 自体が小さい（no_std）ので、陣営ごとに 1 つでも、エンティティごとに 1 つでも持てます。

rubevy の v1 がこの形です。`Script` を付けたエンティティがスケジューラのタスクになり、
毎フレーム「時計をフレーム時間だけ進めて、走れるタスクに予算を配る」だけ。
`sleep 0.1` と書いたタスクはその間 CPU を使わず、譲らないタスクはタイムスライスで横取りされるので、
暴走したスクリプトがフレームを食い潰すことはありません。GC もスケジューラの暇な時間に回します（`GC.scheduler_driven`）。

**実例（2026-09-14）**: SabiRuby Battle では、試合の進行（優先度 10）とロボット 4 体の頭脳（優先度 100）が、1 つの VM の中のタスクです。
ロボットはゲームに `Rubevy.ask("radar", 60.0).pop` と質問し、答えが来るまで CPU を使わずに待ちます。
1 体の頭脳の中で複数のタスクを使う（被弾したら別タスクでブロックを動かす `reflex`）のは次の段階です。

## 6. 機械を見ながら学ぶ — **Playground でできました**

Playground のために作るビジュアライザ（レジスタ、フレーム、環境、Fiber、GC を表示するもの）は、そのままゲームの窓にも出せます。
初心者が Ruby を書き、エンティティが動き、VM を開けば中でレジスタが動いているのが見える。
日本では Ruby が教育で使われています。中が透けて見えるゲームエンジンは、道具というより教材になります。

**いまできること**: SabiRuby Playground（https://sabiruby.github.io/sabiruby-playground/）で、コード → AST → バイトコード → 実行を並べて見られ、
デバッグでは 1 命令ずつ進めて、名前付きのレジスタ、クロージャが残す環境、`raise` がたどる catch テーブル、Fiber、ヒープと GC を見られます。
ゲームの側では、エディタがロボットの頭脳の「最近よく通っている行」を色で示し、スコアボードが 1 フレームに使った命令数を出します
（VM の `task_frames` と `task_instructions`）。

**まだのこと**: Playground のビジュアライザをゲームの窓に出すこと。

## 7. CRuby で試作して、Bevy で出す

スクリプトで使う Ruby の範囲は mruby のものなので、ゲームのルールを CRuby の道具（RSpec など）で先に試して、
そのままエンジンで動かせます。SabiRuby の独自テストは、mruby と CRuby の意味が同じところでは CRuby の出力と照合しています。

**現状**: 変わっていません。SabiRuby Battle の DSL は、ゲームに質問する部分（`Rubevy.ask`）をスタブにすれば CRuby でも動く形に
なっていますが、その道具立ては作っていません。

## 質問への答え: ECS のエンティティは Ruby のオブジェクトになるか

**なります。それが ECS の橋（計画の 3 と 4）の中身です。**

**2026-09-14 の現状**: 3 段のうち 3 段目（書き込みを step の後にまとめて反映する）が入り、それとは別の形として
「質問して答えを待つ」通り道ができました。

* `Rubevy.spawn`／`despawn`／`set_position`／`move_to` はネイティブの中でコマンドを 1 本のキューに積むだけで、
  フレームのスクリプトが走り終わってから system が `Commands` に流します。
* `Rubevy.entity` は「このスクリプトが付いているエンティティ」を整数（`Entity::to_bits`）で返します。
* `Rubevy.ask(kind, *args)` はキューを返し、スクリプトはその `pop` で待ちます。ゲームの system が `ScriptWorld::take_requests` で質問を受け取り、
  普通のクエリで答えを作って `ScriptWorld::answer` で返します（数値、文字列、数値の配列、その表）。
  ゲームの規則は全部 Rust 側に残り、Ruby が頼めるのは「スロットルを 1.0 に」まで、という形です。SabiRuby Battle はこれだけで作っています。

**2026-09-15 の現状**: 1 段目（`Entity` を包む Ruby オブジェクト）と 2 段目（リフレクションで名前から
コンポーネントへ）も入りました。いま書けるのはこの形です。

```ruby
e = Rubevy.entity
tf = e[:Transform]              # {translation: [x, y, z], rotation: [x, y, z, w], scale: [...]}
tf[:translation][0] += 1.0
e[:Transform] = tf              # 名前の挙がったフィールドだけ、フレームの終わりに反映
e.has?(:Velocity)               # true / false
e.components                    # ["Transform", "Sprite", ...]
Rubevy.find(:Npc)               # そのコンポーネントを持つエンティティの配列
```

最初は読みを `e.get(:Transform)` にしていました。mrbc が引数 1 個の `[]` を `OP_GETIDX` に畳み、
VM がそれを入れ子の実行ループで回していて、入れ子の中ではタスクを待たせられなかったからです。
VM を本家と同じ形（普通の送信）に直したので、いまは `[]` で書けます（`get` も残してあります。
`docs/worklog/2026-09-15-ecs-bridge.md`、`2026-09-15-entity-index.md`）。
まだ無いのは、コンポーネントを組み立てて渡す形（`spawn(Sprite.new(...))`）と、クエリをブロックで書く形
（`each(:Enemy, :Transform) { |enemy, tf| ... }`）です。

仕組みは 3 段です。

1. **Rust の値を包む Ruby オブジェクト**。mruby の `RData` にあたるもの（SabiRuby では `ObjKind::Data`）に `Entity` を入れます。
   Ruby からは普通のオブジェクトに見え、GC で回収されるときに Rust 側の `Drop` が走ります。
2. **コンポーネントは Bevy のリフレクションで触る**。Bevy の `Reflect` を使うと、コンポーネントのフィールド名と型が実行時に分かります。
   Ruby の `method_missing` と組み合わせれば、コンポーネントの種類ごとに接着コードを書かなくても、`tf.translation.x` のように名前でたどれます。
   型ごとに手で書くのは、速さが要る少数のものだけです。
3. **書き込みは step の後にまとめて反映**。VM を回す間だけ `&mut World` をホストに貸し、Ruby からの `spawn`／`add`／`despawn` や値の変更は
   Bevy の `Commands` と同じように一度ためて、step が終わってから適用します。VM がホスト呼び出しの途中で Ruby に戻らない作りなので、これが安全にできます。

読み取りはその場の値が返ります。書き込みが遅れて見える点は `Commands` と同じ約束なので、Bevy を知っている人には馴染みがあります。

橋を作るときは「毎フレーム大量に読み書きする」形ではなく、「宣言時に組み立てて、イベントとコルーチンで少しだけ触る」形を先に作ります。
DSL として使う方針に合っていて、性能の弱点が効かない使い方だからです。（2026-09-15: ネイティブからホストの状態へ型付きで届く通り道ができ、
`static` のキューは VM の `host_state` に移り、1 段目の「`Entity` を包む Ruby オブジェクト」も `Rubevy::Entity`（`Data` オブジェクト）として入り、
2 段目のリフレクションも入りました。読みは 1 往復 = 1 フレームなので、この「宣言時とイベント時に触る」方針はそのまま守られています。）

## 補足: Rust のメモリ安全は Ruby 側にも効く（2026-09-12、著者の指摘。2026-09-14 更新）

SabiRuby の VM crate に `unsafe` は 1 か所だけです（命令のバイト値を範囲確認したうえで enum に変換する箇所）。
つまり VM の中で起きうる不具合は「間違った値」「例外」「panic」であって、「メモリ破壊」ではありません。
本家 mruby は C なので、GC のバグや境界の誤りが黙ってメモリを壊し、脆弱性になってきました。SabiRuby ではそれが起きません。

（2026-09-14: 正規表現の移植で一時 15 か所に増えました。検索の途中で VM を使いながらパターンを持つために生ポインタを使っていたためで、
同日、パターンを `Arc` で共有する形に直して 1 か所に戻しました。経緯は `rust-bridge.ja.md` の末尾。）

Ruby 側から見ると次の意味があります。

* Ruby のプログラムがどんな値を作っても、VM がメモリを壊すことはない。ホスト（ゲーム）が道連れになるとしたら panic であって、静かな破壊ではない
* GC の根の漏れは、メモリ破壊ではなく「回収済みのオブジェクトへの参照」として検出される（ストレスモードの assert）
* ネイティブメソッド（Rust で書く拡張）も生ポインタが要らないので、mruby の C 拡張で最も多い落ち方（解放済みメモリの参照、アリーナの溢れ）が無い
* 4 番の「利用者や AI が書いたスクリプトを安全に動かす」の前提が、VM の作りとして満たされている

限界も書いておきます。コンパイラは本家の C のまま（Prism とコード生成）なので、ソースを読む段階は Rust の保証の外です（Prism はよくファジングされていますが）。
panic は安全ですが止まります。ゲームで使うなら「VM は panic しない」を目標にする作業と、ホスト側で `catch_unwind` する備えが要ります。
VM の crate の `unwrap`／`expect`／`panic!` は 2026-09-14 時点で 198 か所（テスト実行用の `mrbtest.rs` を除く。多くは内部の不変条件）です。
メモリ安全は「意味が正しい」ことを保証しません。正しさは本家のテストで測っています（2507 件中 2344 件が通る。残りは理由付き）。

## 補足: 本体は Rust、一部だけ Ruby という使い方（2026-09-12、著者の質問。2026-09-14 更新）

それが rubevy の想定する形そのものです。Ruby は「全部を書く言語」ではなく、Rust のゲームに**部分的に差し込む**ものです。

* Rust が持つもの: ゲームループ、描画、物理、入力、大半の system。今までどおりの Bevy です
* Ruby を付ける場所: `Script` コンポーネントを付けたエンティティ（NPC の挙動）、試合やシーンを組み立てる `.rb`（DSL で spawn）
* Ruby を付けないエンティティには何の影響もない。スクリプトは `Script` が付いたぶんだけタスクになり、Rust の system が決めた予算の中でだけ動く

今の API で書くと次のようになります（SabiRuby Battle の形を簡単にしたもの）。

```rust
// Rust 側: 普通の Bevy。NPC にだけ Ruby を付ける
commands.spawn((Npc, Sprite::from_image(guard_png), Script::new(guard_mrb).with_priority(100)));

// Ruby の質問に答える system（ゲームの規則は Rust 側）
fn answer(mut world: ResMut<ScriptWorld>, npcs: Query<&Transform, With<Npc>>) {
    for request in world.take_requests() {
        let answer = match request.kind.as_str() {
            "where_am_i" => { /* npcs.get(request.entity…) */ Answer::List(vec![x, y]) }
            _ => Answer::Nil,
        };
        world.answer(&request, answer);
    }
}
```

```ruby
# npc/guard.rb: 挙動だけ Ruby。フレームをまたぐ動きは待つだけで書ける
loop do
  x, y = Rubevy.ask("where_am_i").pop
  patrol_to(:point_a); sleep 2
  patrol_to(:point_b); sleep 2
end
```

Ruby 側のミスがゲーム全体に及ばないことも、この形の利点です。命令数の予算と時間の上限で 1 フレームに使える時間が決まり、
例外は `ScriptEnded` メッセージになり、メモリ破壊は起きません。リリース時に Ruby を外したければ、`Script` を付けなければよいだけです。

2026-09-12 の時点では「エンティティごとに VM」「イベントの受け口がない」でしたが、いまは 1 つの VM にタスクを並べる形になり、
Ruby からの質問に system が答える通り道（`Rubevy.ask`）ができ、2026-09-15 に ECS の橋の 1・2 段目と、
Bevy のイベントを Ruby に届ける受け口（`Rubevy.subscribe` と `ScriptWorld::publish`）も入りました。

## 補足: Rust と Ruby の相互呼び出し（2026-09-12、著者の質問。2026-09-14 更新）

どちらの向きもできます。mruby の C 拡張と `mrb_funcall` に相当するものが、そのまま Rust にあります。

* **Rust → Ruby**: `vm.funcall(receiver, method_sym, &args, block)`、ブロックなら `vm.call_block(blk, &args)`。戻り値は `Result<Value, VmError>`
* **Ruby → Rust**: ネイティブメソッドは `fn(&mut Vm, self, &[Value], block) -> VmResult<Value>` の Rust 関数。`vm.define_method(class, "name", f)` で登録する
* **Ruby → Rust → Ruby**: ネイティブの中で `vm.funcall` を呼べる。VM は入れ子の実行ループを Rust のスタック上で回す（本家の `mrb_funcall` → `mrb_vm_run` と同じ形）。
  何段でも入れ子にできる

```rust
fn each_enemy(vm: &mut Vm, _self: Value, args: &[Value], blk: Value) -> VmResult<Value> {
    for e in enemies() {                       // Rust 側のデータ
        let obj = entity_object(vm, class, e);  // Entity を Ruby オブジェクトに（rubevy の `entity_object`）
        vm.call_block(blk, &[obj])?;           // Ruby のブロックを呼ぶ。例外は `?` で伝わる
    }
    Ok(Value::Nil)
}
```

本家と違って良くなる点が 1 つあります。Ruby 側の例外は longjmp ではなく `Err` として Rust に戻るので、`?` で素直に伝えられ、
途中の Rust の値の後始末（`Drop`）が必ず走ります。本家の C 拡張では longjmp が C の途中の処理を飛び越えるので、資源の解放を自分で守る必要がありました。
（この比較は `rust-bridge.ja.md` の 4 章で、GC アリーナ、スレッド、ビルド、ブラウザまで広げて書いた。）

約束事（本家と同じもの）:

* ネイティブの実行中は GC が回収しない（`native_active`）。Rust の手元にある `Value` は安全だが、長いネイティブは GC を遅らせる
* ネイティブの境界をまたいで Fiber を切り替えることはできない（`FiberError`。本家と同じ制約）
* ネイティブから呼んだ Ruby（入れ子の実行ループ）の中では、タスクを切り替えられない。ネイティブが戻るまで、その
  タスクは自分の番を手放さない

約束事（SabiRuby で足したもの、2026-09-14）:

* 上の 3 つ目の穴を塞ぐために、ホストが時間の上限（`task_run_limits`）をかけていれば、入れ子の中で上限を超えたタスクには
  `Task::Overrun` が投げられる。例外なので、ネイティブの Rust の値もきちんと片付けながら抜ける
* ネイティブメソッドは関数ポインタのほかにクロージャでも登録でき（`define_closure`、2026-09-15）、ホストの状態には `Vm` の型付きの
  `host_state` で届く。本家の `mrb->ud`（`void*`）に当たるものが型付きになった形。Rust の関数をそのまま登録する `define_fn` もある
